## Зачем создан проект

Это Python-компонент для [форка nlbwmon](https://github.com/anideth/nlbwmon). Задача — получать события жизненного цикла conntrack и делать сведения об отдельных соединениях доступными для поиска и анализа в OpenSearch **без второго конкурирующего сборщика conntrack на роутере**.

На роутере nlbwmon продолжает обычный учёт трафика и дополнительно отправляет события `NEW` и `DESTROY` в формате JSONL (`nlbwmon-flow-v1`). Коллектор принимает их, сохраняет в SQLite WAL и передаёт в OpenSearch. Это средство наблюдаемости, **не** захват пакетов, не NetFlow/IPFIX и не система гарантированной доставки.

## Авторство, использование ИИ и зрелость

Автор проекта — DevOps/инфраструктурный инженер с большим опытом Linux и сетей, но ограниченным опытом профессиональной разработки программ. Код Python создавался со значительной помощью инструментов ИИ; архитектура, развёртывание и испытания выполнялись в собственной лаборатории. Независимого аудита безопасности и широкой проверки совместимости пока нет.

**Статус: опубликованная экспериментальная beta `v0.1.0-beta.1`.** Наблюдения за работающим сбором данных не доказывают полноту событий, корректность всех NAT-сценариев или поддержку любых версий OpenWrt и OpenSearch. Предназначено прежде всего для лаборатории и self-hosting.

## Архитектура

```text
OpenWrt / nlbwmon fork (NEW, DESTROY)
    -> TCP JSONL (доверенная сеть / защищённый туннель)
    -> flow_collector.py :5517
    -> SQLite WAL (очередь принятых событий)
    -> OpenSearch Bulk API (scripted upsert)
    -> conntrack-flows-YYYY.MM.DD
    -> OpenSearch Dashboards / Grafana
```

**Fluent Bit для этой схемы не нужен.** Для каждого соединения используется один документ с устойчивым идентификатором. Необязательный PTR-поиск DNS-имён выполняется асинхронно.

## Жизненный цикл соединения

- **NEW:** создаётся документ с `flow.status=active`, временем начала и исходными адресами/портами. Окончательных счётчиков трафика ещё нет.
- **DESTROY:** тот же документ обновляется до `flow.status=closed`, добавляются время завершения, длительность и итоговые счётчики байтов/пакетов.
- **DESTROY без NEW:** создаётся закрытый документ, поскольку событие NEW могло быть пропущено.
- **Повторные события и поздний NEW:** сценарии обрабатываются идемпотентно, закрытый документ не открывается заново.
- **Потерянный DESTROY:** документ может оставаться `active` до удаления индекса по политике хранения. Автоматическое определение устаревших соединений пока **не реализовано**.

Промежуточные UPDATE и периодические снимки счётчиков каждого соединения не сохраняются. Значения трафика после DESTROY — накопленные счётчики conntrack, а не обязательно объём полезных данных приложения. NAT может влиять на интерпретацию исходных и преобразованных адресов.

Подробно: [жизненный цикл и поля](docs/LIFECYCLE_SETUP.md).

## SQLite, OpenSearch и гарантии

SQLite используется как постоянная очередь **уже принятых** событий (WAL, `synchronous=FULL`), но не как очередь PTR-заданий. После успешной записи событие переживает перезапуск коллектора и временную недоступность OpenSearch. Но потерянные на роутере или до сохранения в SQLite события восстановить нельзя.

**PTR в RC:** результаты DNS кешируются по IP в SQLite (`dns_cache`), отдельные `dns_jobs` для каждого соединения не создаются. Поздние обновления PTR выполняются фоновым потоком через Bulk API; очередь в памяти ограничена 2000 соединениями и 30 секундами, поэтому после перезапуска или переполнения часть PTR может отсутствовать.

Коллектор отправляет обновления через **OpenSearch Bulk API**, используя скриптовые обновления документов. Нужны разрешённые скрипты, `_source` и корректный mapping индексов `conntrack-flows-*`. Схема API основана на возможностях OpenSearch 1.0+, однако совместимость со всеми выпусками не проверена.

Для Dashboards используйте индекс `conntrack-flows-*` и поле времени **`flow.started_at`**. Индекс выбирается по дате начала соединения в UTC. Для настройки mapping, ISM и Discover см. [LIFECYCLE_SETUP.md](docs/LIFECYCLE_SETUP.md).

**Ограничения:** нет прикладного подтверждения роутеру, гарантии exactly-once или полного восстановления. Переполнение очереди, проблемы диска, TCP и Netlink могут приводить к потерям. `--max-events` ограничивает основную очередь событий, но не весь объём SQLite. Права на OpenSearch должны быть минимально необходимыми.

## Возможности

- Приём `NEW`/`DESTROY` по TCP в формате `nlbwmon-flow-v1`.
- Отдельные документы для соединений с `router_name`, IP, портами, протоколом, временем и итоговыми счётчиками.
- SQLite WAL для сохранения событий до доставки в OpenSearch.
- Пакетная отправка в OpenSearch с повторными попытками.
- Необязательное асинхронное PTR-обогащение с кешем.
- Работа на Python 3 без сторонних Python-библиотек.
- Пример systemd-сервиса и автоматические тесты.

## Требования и быстрая установка

Нужны Linux (примеры для Debian/systemd), Python 3 со стандартными `sqlite3` и `ssl`, постоянное хранилище и OpenSearch с разрешёнными скриптовыми обновлениями.

**Начинайте с [INSTALL.ru.md](INSTALL.ru.md)** — там приведены проверка исходников, отдельная учётная запись, секреты, systemd, OpenSearch, подключение роутера, диагностика и откат. Не копируйте команды с демонстрационными адресами без замены параметров.

```sh
python3 -m py_compile flow_collector.py flow_lifecycle.py flow_opensearch.py flow_writer.py dns_resolver.py
python3 -m unittest -v test_dns_resolver test_flow_lifecycle test_flow_opensearch test_flow_writer test_flow_collector
python3 flow_collector.py --help
```

Основные параметры: `--listen` (по умолчанию `127.0.0.1`), `--port` (`5517`), обязательные `--db` и `--url`, `--bulk-size` (`100`), `--max-events` (`100000`), `--ca-file`, `--password-file` или `--api-key-file`, необязательные `--dns` и `--dns-server`. Не используйте `--insecure` для обычной эксплуатации.

## Проверка и эксплуатация

**Изолированные тесты на существующем OpenSearch:** для тестового коллектора укажите `--index-prefix conntrack-flows-tests` (по умолчанию остаётся `conntrack-flows`). Это направляет **и Bulk-записи, и асинхронные PTR-обновления** в `conntrack-flows-tests-YYYY.MM.DD`. До подключения VM создайте отдельный шаблон индекса и учётную запись с минимальными правами только на `conntrack-flows-tests-*`. По возможности используйте отдельные тестовые учётные данные с минимальными правами. Если в лаборатории используется существующая учётная запись записи, явно документируйте исключение и проверяйте изоляцию индексов. Рабочие шаблоны не меняйте.


После запуска проверьте порт `5517`, сообщения systemd и очередь SQLite. Создайте тестовое соединение на роутере и убедитесь, что NEW создаёт `active`, а DESTROY обновляет **тот же** документ до `closed`. Рост очереди может указывать на проблемы связи, OpenSearch, прав или mapping.

Для обновления сохраните идентификатор текущего коммита, unit и согласованную резервную копию SQLite. Используйте фиксированную протестированную ревизию и не удаляйте накопленные события при откате.

## Безопасность и конфиденциальность

События содержат IP-адреса, порты, сетевые идентификаторы и, при включённом PTR, имена хостов. Эти данные могут быть конфиденциальными. Не публикуйте реальные конфигурации, адреса, пароли, ключи, дампы событий и информацию работодателя.

Ограничьте TCP-порт коллектора доверенными источниками или используйте защищённый туннель. Для OpenSearch применяйте HTTPS с проверкой сертификата и минимальные права. До открытия репозитория необходим аудит **всей истории Git**, а не только текущих файлов.

## Исторический режим агрегирования

В репозитории также находится `aggregator.py` — предыдущий режим обработки текстовых conntrack DESTROY и отдельных JSONL-событий. Он группирует завершённые соединения по временным окнам и отправляет результаты в Fluent Bit, обычно через TCP `5515 → 5516`, в индексы `conntrack-agg-*`.

Это **не** путь установки нового lifecycle collector. Для изучения прежнего режима доступны [английский README](README.md#legacy-aggregator-architecture), [DEPLOYMENT.md](docs/DEPLOYMENT.md) и примеры в [examples/](examples/). Не смешивайте его агрегированные документы с `conntrack-flows-*`.
